**先说结论**：这个项目里的每一个技术决定，几乎都是「内容变长」逼出来的——额度不够、模型变慢、章节必须存在、容器要装得下整本。它和 Scripts to Audiobook 是互补关系：一个处理几分钟的对话，一个处理几十万字。

## 起点：我只是想躺着听书

做这个项目的初心很具体：总盯着屏幕看电子书伤眼睛。屏幕上的字再清晰，看两小时也会累；而音频不需要眼睛参与，播放着就行。

这个理由听起来不像产品经理该说的话，但它决定了很多后续选择——比如我从不考虑「看」的功能，只考虑「听」的连续性。

## 第一个约束：额度

Scripts to Audiobook 里，一段对话几分钟，用云端的 TTS 完全够——各家都有免费额度，短内容跑完还剩很多。

整本书不一样。几十万字意味着几小时的音频，同样的免费额度会被一次性吃掉，甚至直接 cover 不了。所以这个项目的默认路径变成了**本地模型**：Intel Mac 上默认 Kokoro（82M 参数、CPU 推理），Apple Silicon 上默认 Qwen3 MLX。

代价很实在：模型要下载、要占几百兆、Kokoro 还卡在 Python 3.12 以下。但换来的是「不按字数计费」，这对整本书是决定性的。

## 第二个约束：速度

本地模型慢。即使开多线程，跑完一整本书也要花时间。

但我判断这不成问题——因为**消费发生在生成之后**。我可以在睡前把一本书丢进去，第二天早上再听；慢的是机器，不是我的时间。真正不能接受的是「等一分钟才能听一句对话」，那是短内容的场景，不是这个项目的场景。

所以这个项目没有为「实时」做任何设计，它更像一个批处理任务。

## 第三个约束：章节

书的章节不是我发明的，书本身就有。所以切分按自然结构走：目录有什么，章节就是什么。

真正的麻烦是格式。EPUB、MOBI、AZW3 的结构相对规整，PDF 不是——它是排版的产物，不是结构的产物，识别出来常常带噪声。这类文件我会允许手动改：`chapters` 可以列出、查看、编辑某一章。

这里有个细节我坚持了：**编辑稿单独保存，原文永不覆盖**。改过的章节会带一个 `[edited]` 标记，转换时优先用编辑稿。改错可以重来，原文始终在。

## 第四个约束：容器

为什么默认 M4B？很实际的原因：我的开发环境是 macOS，M4B 是苹果生态里自带章节信息的格式，播放器能直接显示章节、记住进度。

但我没有只做一种输出。单章可以出 MP3——想先听一章就用它；整本最后合成一个 M4B——有章节标记，也能一口气听下去。**同一套内容，两种消费方式。**

## 免费供应商：开箱即用，但把风险写在明面上

除了本地模型，项目也接了 Edge、ElevenLabs、讯飞、百度这些云端供应商。保留它们的理由很简单：免费，而且开箱即用——不用下载模型，填个 key 就能跑。

Edge TTS 有一条需要在 README 里写清楚的事实：它不是微软的官方 API，长时间批量使用可能违反服务条款。我把这句话和六个替代方案一起放在文档里，没有藏起来。

这是一个取舍：对个人和研究用途，它足够方便；对商业用途，你该换成本地模型或正规 API。文档写清楚，选择权交给使用者。

## 版本是被 bug 推着走的

从 v0.1.9 到 v0.2.0，一个月里发了六个版本。驱动它们的不是新功能清单，而是 bug，和一些刚开始没想到的体验细节——比如某些 PDF 切出来的章节是碎的，比如转换中断之后怎么续。

这类迭代不会写进 release note 的亮点里，但它是这个项目真正变好用的原因。

## 如果做成商用产品，第一件事是把选择收走

现在这个项目让用户自己选供应商、自己调音色。如果真做商用，我会反着来：**把供应商全换掉。**

理由不是省钱，是质量一致性。商用产品需要对每个音色有足够把控，才能承诺「听起来是这样」。更进一步的做法是：分析上传的文档，判断它偏叙事还是偏对话，自动匹配对应的供应商和音色——用户不需要懂 TTS，只需要拿到一个好听的版本。

让用户选，是把复杂度推给用户；替用户选，才需要对结果负责。
